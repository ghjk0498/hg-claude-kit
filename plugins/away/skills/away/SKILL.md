# 자리 비우기 전 점검

목적은 하나다. 돌아와서 첫 턴에 **식은 캐시에 긴 컨텍스트를 다시 쓰는 비용**을 줄이되, 이어갈 작업의 맥락은 잃지 않는 것.

## 1. 측정

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/skills/away/away_check.py"
```

세션 id는 `$CLAUDE_CODE_SESSION_ID`에서 읽는다. 출력에서 `context tokens`, `baseline`, `conversation part`, `after compact`, `cache TTL`, `cache now`, `resume, cold`, `compact first`, `break-even`을 쓴다.

**바닥값(`baseline`)**은 압축해도 남는 부분이다. 시스템 프롬프트, 도구 정의, 다시 주입되는 AGENTS.md·메모리·스킬 목록이 여기에 든다. 새 세션도 이 값에서 시작하므로 압축이나 핸드오프로 줄지 않는다. 스크립트는 이 값을 가정하지 않고 다음 순서로 잰다(괄호에 출처를 표시한다).
1. `own-compact`: 이 세션의 마지막 압축 직후 첫 턴. 실측값이다
2. `project-compact`: 같은 폴더 최근 세션들의 압축 직후 첫 턴 − 요약(`postTokens`)의 중앙값
3. `first-turns`: 같은 폴더 최근 세션들의 첫 턴 중앙값
4. `default`: 스크립트 상단 `DEFAULT_BASELINE`(추정)

압축 후 컨텍스트는 바닥값 + 요약(`after compact`)이고, 손익분기도 이 값으로 계산한다. `shared prefix` 줄은 공통 앞부분이 다른 세션 덕에 아직 따뜻할 때의 복귀 비용 추정이다. 이 부분은 식은 복귀와 압축 양쪽에서 똑같이 빠지므로 **판정(손익분기)은 바뀌지 않는다**.

TTL은 가정하지 않고 마지막 캐시 쓰기의 `cache_creation` 분할(1h/5m)에서 읽는다. 이 값에 요금제·API 키·한도 초과 강등이 이미 반영돼 있다. 기록이 없으면 `NO DATA`로 표시하고 5분으로 본다. 단가는 스크립트 상단 `PRICES`에 있다(2026-10-06 기준). 모델 단가가 바뀌면 그곳만 고친다.

## 2. 묻기 (AskUserQuestion 한 번, 질문 두 개)

- **얼마나 비우나**: TTL 미만 / TTL 이상 (`cache TTL` 값 기준. 5분이면 사실상 늘 «이상»)
- **돌아와서 무엇을 하나**: 이 일을 이어감 / 다른 일 / 아직 모름 / **일을 맡겨 두고 떠남**(백그라운드 작업·서브에이전트·사이드 세션이 비운 사이 끝남)

사용자가 이미 말했으면 묻지 않는다.

캐시는 떠난 시각이 아니라 **마지막 턴**부터 식는다. 맡긴 일이 끝나면 완료 알림으로 세션이 한 턴 깨어나고 타이머가 다시 1시간이 된다. 문제는 그 뒤 1시간 넘게 아무도 오지 않는 구간이고, 완료 턴은 미리 지시해 둘 수 있는 마지막 턴이다.

## 3. 판정

| 조건 | 권장 |
|---|---|
| TTL 미만 | **그대로.** 캐시가 따뜻하게 남아 있다 |
| 최근 몇 턴이 버릴 경로(막다른 시도·잘못된 방향) | **`/rewind`로 그 앞까지 되돌린 뒤** 아래 판정을 다시 한다. 캐시에 이미 있는 앞부분으로 잘리므로 가장 싸게 줄이는 방법이다 |
| 컨텍스트 < `break-even` (Opus 5.5·바닥값 약 75K 기준 약 120K, 대화분 약 45K) | **그대로.** 압축 비용이 아낄 돈과 비슷하고 세부만 잃는다 |
| `break-even` 이상, 대화분 < 200K, 같은 일을 이어감 | **떠나기 전에 `/compact`** |
| `break-even` 이상, 다른 일 · 남은 일이 브리프로 설명됨 | **fresh 핸드오프**(새 세션). 이 세션은 그대로 둔다 |
| 대화분(`conversation part`) 200K 이상 | 압축 또는 fresh 핸드오프. 비용에 더해 긴 컨텍스트는 정확도도 떨어진다 |
| 이미 `COLD` | 압축하지 않는다(식은 상태로 전체를 읽게 됨). 이어갈 거면 그대로 두고, 다른 일이면 새 세션으로 |
| 일을 맡겨 두고 떠남, 아직 시작 전이고 일이 크고 독립적 | **처음부터 fresh 사이드 세션에 맡긴다.** 이 세션은 더 길어지지 않고, 돌아와서 필요한 쪽만 연다 |
| 일을 맡겨 두고 떠남, 이 세션에서 돌아감 | **완료 턴에 인계 파일을 쓰게 한다**(아래 5단계). 복귀는 새 세션에서 그 파일만 읽는다. 컨텍스트가 break-even 이상이고 아직 따뜻하면, 맡기기 전에 `/compact`부터 하는 것도 함께 권한다 |

판단 기준은 다음 한 줄이다. 남은 일이 이 대화에서 알아낸 것에 크게 기대면 압축하고, 짧은 브리프로 설명되면 핸드오프한다.

결과는 표 한 장으로 보여 준다: 컨텍스트(바닥값 · 대화분) · 캐시 상태 · 식은 복귀 비용 · 압축 비용 · 권장 · 아끼는 금액.

## 4. 보존 (압축·핸드오프일 때만)

요약이나 브리프에서 빠지면 곤란한 것을 먼저 오래 남는 곳에 적는다.
- 내린 결정, 다음 할 일 → 메모리 또는 프로젝트의 후속 작업 대장
- 커밋하지 않은 변경, 브랜치, 진행 중인 백그라운드 작업 → 한 줄 상태 메모

커밋·푸시는 프로젝트 규칙을 따르고, 규칙이 없으면 묻는다.

## 5. 실행

- **그대로**: «정리할 것은 없습니다. 6단계 메모만 남깁니다.»라고 말하고 6단계로 간다.
- **압축**: `/compact`는 사용자 명령이라 내가 실행할 수 없다. 남길 것을 지정한 한 줄을 만들어 준다. 예:
  `/compact 남길 것: <현재 목표>, <결정 사항>, <다음 단계>, <변경 파일 경로>. 버릴 것: 탐색 로그, 도구 출력 원문`
- **맡기고 떠남(인계 파일)**: 완료 턴에서는 `/compact`를 실행할 수 없으므로, 대신 압축과 같은 효과를 내는 파일을 남긴다. 맡기는 지시 끝에 다음을 붙인다.
  «끝나면 결과 · 내린 결정 · 검토했다 버린 대안과 이유 · 실패와 원인 · 막힌 것(사람 답 필요 포함) · 다음 할 일 · 변경 파일과 브랜치를 `<프로젝트>/.claude/handoff-<날짜>.md`(git이 없으면 스크래치패드)에 정리하고, 파일 맨 위에 6단계의 «복귀 메모 3줄»(어디까지 · 첫 행동 · 내가 정할 것)을 완료 시점 기준으로 먼저 쓰고, 그 밖의 일은 시작하지 말고 멈춰.»
  사용자에게는 돌아와서 새 세션을 열고 «`<파일>` 읽고 이어서»라고 시작하라고 알린다. 긴 세션을 다시 깨우지 않는 것이 핵심이다. 인계 파일은 커밋하지 않는다.
- **핸드오프**: 데스크톱 앱이면 `start_session`(fresh)으로 브리프를 넘긴다. 브리프에는 목표, 관련 파일, 완료 기준, 4단계에서 적은 위치를 쓴다. CLI면 브리프를 붙여 넣을 수 있게 출력한다.

## 6. 복귀 메모 (판정과 무관하게 항상)

떠나는 순간 직접 계획을 세우면 끊긴 일에 남는 주의가 줄어든다(Leroy & Glomb 2018, Organization Science). 돌아왔을 때 복귀 단서 역할도 한다. 비용 절감과는 별개로, 사람 쪽 비용을 줄이는 단계다. 3줄 이내.

1. 어디까지: <마지막 완료 지점> · <미커밋/브랜치 상태, 돌아가는 일>
2. 첫 행동: <파일·명령 수준으로 구체적으로>
3. 내가 정할 것: <없으면 «없음»>

에이전트는 초안을 쓰고 «이대로 / 한 줄 고치기»를 묻는다(2단계 질문에 합쳐도 된다). 사용자가 직접 고쳐 쓰는 행위가 닫힘 효과의 핵심이라, 초안을 읽기만 하게 두지 않는다. 직접 쓰기를 강제하지는 않는다(떠나는 순간의 마찰이 커서 건너뛰게 된다).

- 응답 맨 끝에 보여 준다. 별도 파일은 만들지 않는다.
- **핸드오프**: 같은 3줄을 브리프 맨 위에도 넣는다(새 세션에서는 옛 응답이 안 보인다).
- **인계 파일**: 5단계 지시문대로 완료 시점 기준으로 맨 위에 쓰게 한다. 지금 쓴 메모를 그대로 옮기지 않는다(복귀 때는 낡는다).

## 하지 않을 것

- 복귀 메모를 3줄 넘게 쓰거나 4단계 내용을 반복하지 않는다. 길면 읽는 비용이 복귀 비용을 넘는다. 예상 소요 시간은 쓰지 않는다(추정이 부정확하다).
- 캐시를 데우려고 깨우기(ScheduleWakeup, `/loop`, 주기적 메시지)를 권하지 않는다. 계산만 보면 손해가 아니다. 캐시 읽기가 TTL을 공짜로 다시 1시간으로 돌리고 읽기 단가도 싸서, 스크립트의 `keep-alive ping` 줄처럼 공백이 꽤 길 때까지 핑이 식은 복귀보다 쌀 수 있다. 그래도 권하지 않는 이유는 셋이다. ScheduleWakeup은 `/loop` 전용이고 캐시 유지 목적의 사용을 금지한다. 핑마다 컨텍스트가 불어난다. 인계 파일이나 압축이 더 싸고 깔끔하다. 사용자가 직접 묻는 경우에만 이 계산을 보여 준다.
- 복귀 직후 모델이나 노력 수준 바꾸기를 권하지 않는다. 캐시는 모델별로 따로 있고 effort를 바꿔도 다시 쓴다. 바꿀 거라면 어차피 식은 뒤에 바꾼다.
- 숫자를 추정하지 않는다. 스크립트가 실패하면 실패했다고 말하고 `/context`로 확인해 달라고 한다.
